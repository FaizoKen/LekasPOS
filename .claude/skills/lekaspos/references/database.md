# Database

`app/src/main/java/com/lekaspos/data/db/Schema.kt` is the authoritative DDL. This file explains
the rules behind it. Keep both in sync.

## 1. Engine choice and setup

- **Raw framework SQLite** (`android.database.sqlite`) wrapped by `Db`. Not Room: we need
  hand-tuned SQL (FTS4, partial indexes, compiled statements in hot paths, LWW merges,
  summary tables) and no annotation processing. (WorkManager still pulls Room in for its own
  private database; that is fine.) See `docs/DECISIONS.md` D-001.
- One file: `lekaspos.db` in the app's database dir. Opened by `DbOpenHelper`
  (`SQLiteOpenHelper`) with `setWriteAheadLoggingEnabled(true)`.
- `onConfigure`: `setForeignKeyConstraintsEnabled(true)`.
- `onOpen` (primary connection): `PRAGMA synchronous=FULL` (a committed sale survives power
  loss), `PRAGMA journal_size_limit=4194304`, `PRAGMA cache_size=-4000` (4 MB),
  `setMaxSqlCacheSize(100)`.
- Writes only via `Db.write {}` on the `db-writer` thread; reads via `Db.read {}`.
- WAL checkpoints: automatic (1000 pages). Before copying the DB file (backup) the writer is
  paused and `PRAGMA wal_checkpoint(FULL)` runs (TRUNCATE needs 3.8.8).

## 2. SQLite 3.8.4 (Android 5.0) — what we may not use

| Not available on API 21 | Use instead |
|---|---|
| UPSERT `ON CONFLICT DO UPDATE` (3.24) | `UPDATE …`; if `changes()==0` then `INSERT` (same transaction) |
| `RETURNING` (3.35) | we generate IDs in Kotlin before inserting |
| Window functions (3.25) | aggregate in SQL + finish in Kotlin |
| Row values `(a,b) < (?,?)` (3.15) | `a < ? OR (a = ? AND b < ?)` |
| Expression indexes (3.9) | store a normalized column (e.g. `name_key`) and index it |
| json1 functions | parse JSON in Kotlin |
| FTS5 / `unicode61` tokenizer not guaranteed | FTS4 `tokenize=simple` + our own normalization |
| `ALTER TABLE … RENAME COLUMN / DROP COLUMN` | table rebuild migration (create new, copy, drop, rename) |
| Generated columns, `IIF`, `FILTER`, `NULLS FIRST/LAST`, `unixepoch()` | plain `CASE`, `COALESCE`, Kotlin |
| `PRAGMA optimize` (3.18) | `ANALYZE` after bulk imports |
| `VACUUM INTO` (3.27), `ATTACH` (disables WAL on Android) | stream rows into a second DB file |

Available and used: WAL, partial indexes, `WITHOUT ROWID`, CTEs, FTS4 with `prefix=`,
`INSERT OR IGNORE`, `printf`, `instr`.
Every instrumented DB test must pass on the API 21 emulator image — that is the real check.

**Partial indexes on SQLite 3.8 (verified on the API 21 image, SQLite 3.8.6):**
- Predicate `WHERE deleted = 0`: used when the query repeats `deleted = 0` literally.
- Predicate that is exactly `WHERE col IS NOT NULL`: used for `col = ?` / ranges against a
  constant or bind parameter, and for `col IS NOT NULL` on its own.
- **Never** used inside a correlated subquery (`r.col = outer.id` → full scan per outer row,
  i.e. O(n²)). Use an aggregate `GROUP BY` + join, or loop in Kotlin with `col = ?`.
- **Never** used when the predicate mixes `IS NOT NULL` with other terms
  (`WHERE deleted = 0 AND sku IS NOT NULL` is dead weight). Only the two forms above are allowed.
- `QueryPlans` (perf suite, `PerfSuiteTest`, `QueryPlansTest`) catches violations — register
  every hot query (`HOT_QUERIES`) and every rebuild/maintenance statement
  (`MAINTENANCE_QUERIES`).

## 3. Conventions

| Thing | Convention |
|---|---|
| Table names | singular `snake_case`: `product`, `sale_line` |
| Primary key | `id INTEGER PRIMARY KEY` (rowid alias), value generated by the app |
| Money | `INTEGER` minor units: `price`, `cost`, `total`, `amount`, `tax`, `discount` |
| Quantity | `INTEGER` milli-units: `qty`, `pack_qty`, `low_stock`, `stock_qty` |
| Rates | `INTEGER` basis points: `rate_bp`, `tax_bp` |
| Timestamps | `INTEGER` epoch ms UTC, names end in `_at` |
| Business day | `day INTEGER` = local epoch day in the store time zone |
| Booleans | `INTEGER` 0/1 |
| Enums | `INTEGER` codes defined once in `:core` (`com.lekaspos.core.model.Codes`); never renumber |
| Normalized text | `*_key` columns (lowercase, accents stripped) for sorting/prefix search |
| Snapshots on documents | lines copy name, barcode, unit, price, cost, tax, category at sale time |

## 4. Sync classes (every table has exactly one)

| Class | Meaning | Required columns | Merge on import |
|---|---|---|---|
| **LWW** | editable master data | `deleted`, `created_at`, `updated_at`, `ver_hlc`, `ver_dev`, `fver` | per-field last-writer-wins by `(hlc, device_no)` |
| **EVENT** | append-only facts | `hlc` (+ `*_at`) | `INSERT OR IGNORE` by `id`; update derived data only if inserted |
| **LOCAL** | device-only state | — | never synced, excluded from snapshots |
| **DERIVED** | caches rebuildable from EVENT/LWW rows | — | recomputed locally; included in snapshots for speed |

LWW field versions: `ver_hlc`/`ver_dev` are the base version of the whole row; `fver` holds
the versions of fields changed after that, as `field:hlc:dev` entries joined by `;` (NULL if
none). The version of field *f* is its `fver` entry, else the base version. Deletion is the
LWW field `deleted = 1` (a tombstone); rows referenced by history are never hard-deleted.

## 5. IDs

- `id = (device_no shl 41) or seq` — 22-bit random `device_no` (1..4,194,303) chosen at first
  launch, 41-bit per-device sequence shared by all tables. Always positive, fits `Long`.
- `device_no = 0` is reserved for **seed rows** that every device creates identically
  (default roles, payment methods) — same IDs everywhere, `ver_hlc = 0` so any edit wins.
- The sequence is reserved in blocks (meta key `id_reserved`) in its own committed
  transaction before use, so a crash can only create gaps, never reuse.
- LOCAL tables (`cart`, `cart_line`, `outbox`, `print_job`) use plain rowids; cart and
  cart-line IDs are assigned in memory by `CartSession` (seeded from `MAX(id)`, D-029).
- The default owner (`staff` id 1) is a seed row, created with `INSERT OR IGNORE` on open.
- Device-only settings (printer, drawer, SPP scanner, camera) are `meta` rows under `dev.*`
  (D-030); store-wide settings are `setting` rows (LWW per key, keys in `SettingKeys`).
- Receipt numbers are per device and per document kind: `{receipt_prefix}{kind}{seq:06}`.

## 7. Derived data rules

- **Stock level** of a product = qty of its latest `stock_count` (by `(hlc, device_no)`) +
  Σ `stock_movement.qty` after that count + Σ `sale_line.stock_qty` of non-voided sales
  after that count. `stock_level` caches it and is updated in the same transaction as each
  inserted movement/line/count/void. `StockDao.rebuild(productId?)` recomputes from events.
- `sale_line.stock_qty` is the signed stock effect in base units (sale: −qty×pack; refund with
  restock: +; untracked product or refund without restock: 0).
- `sale.status` (voided) and `sale.refunded` are derived from `sale_void` and refund
  documents; when a sale arrives after its void/refund (out-of-order sync) they are computed
  on insert.
- Summary tables (`sum_*`) are updated incrementally with every sale/refund/void (local or
  imported) and can be rebuilt with one `INSERT … SELECT … GROUP BY` per table.
- Any derived value must be recomputable from EVENT + LWW rows alone, independent of the
  order in which events arrived.

## 8. Query rules

- Every query on a table that can grow large (`sale`, `sale_line`, `payment`,
  `stock_movement`, `audit_log`, `credit_entry`) must use an index range. The perf suite runs
  `EXPLAIN QUERY PLAN` on registered hot queries and fails on a full scan.
- Pagination is keyset, never `OFFSET`. Write it so the first term is an index range:
  `WHERE sold_at <= ? AND (sold_at < ? OR id < ?) ORDER BY sold_at DESC, id DESC LIMIT 50`
  (a bare `a < ? OR (a = ? AND b < ?)` may not use the index on old SQLite).
- Partial indexes are only used when the query repeats the index predicate literally
  (`AND deleted = 0`).
- Reports read `sum_*` tables; drill-downs read detail tables by indexed ranges.
- Joins whose order matters (FTS first, barcode index first) use `CROSS JOIN`, which SQLite
  never reorders.
- Register every new hot query in its DAO's `HOT_QUERIES`; `QueryPlans` (perf suite and
  `PerfSuiteTest`) fails on a full scan of a large table or a sort where index order is expected.
- Product search (`ProductDao.search`):
  - FTS4 `product_fts` (`tokenize=simple`, `prefix="2,3"`), docid = product id, body =
    normalized name + SKU (barcodes are *not* in FTS). Text is normalized in Kotlin (`:core`
    `SearchText`): lowercase, Latin accents removed, punctuation → space, CJK split into
    single-character tokens. Queries become `tok1* tok2*` (all required).
  - The FTS candidate set is capped (`FTS_CANDIDATES` = 2000) before joining/sorting, so a very
    common prefix costs the same as a rare one.
  - Digit-only input (2+ digits) first matches barcode/PLU prefixes on the barcode index.
  - A single Latin letter/digit uses the `name_key` index range; a single CJK character uses FTS.
  - `product_fts` is rewritten in the same transaction as the product change (no triggers).
- Android API level traps in DAO code: `Map.putIfAbsent/getOrDefault/computeIfAbsent`,
  `java.util.Optional`, streams, `String.join` are API 24+; lint (NewApi) fails the build.

## 9. Migrations

- `DB_VERSION` in `Schema.kt`; `Migrations.kt` holds `Migration(from, to)` steps; `onUpgrade`
  runs them in order inside the open-helper transaction. `onDowngrade` refuses (throws a
  clear error; the UI offers restore from backup).
- After Phase 1 has been installed by the tester, never edit a shipped version's DDL. Change
  = new version + migration + schema snapshot `app/src/androidTest/assets/schemas/<v>.sql`.
- `MigrationTest` (instrumented): for every stored snapshot `k`, create a DB from `k.sql`, run
  migrations to latest, and assert the normalized `sqlite_master` equals a fresh install.
  `SchemaSnapshotTest` fails if the latest snapshot file is missing or stale.
- Column changes use the rebuild pattern (API 21 has no RENAME/DROP COLUMN). Rebuild inside
  the migration transaction with `PRAGMA foreign_keys` handled by `DbOpenHelper`.
- `ALTER TABLE … ADD COLUMN` is fine on 3.8: SQLite appends `, <column def>` to the stored
  CREATE text, so a fresh DDL with the new columns *last* (same spelling) matches a migrated DB.
- History: v1 (Phase 1), v2 (Phase 3, D-034: count sessions, count expected/cost, movement log index), v3 (Phase 4, D-040: `credit_entry.shift_id`, `credit_entry_shift`, `sale_void_shift`, seed role permissions), v4 (Phase 5, D-043: `sum_month_product`, REPORTS permission for the unedited manager role).
